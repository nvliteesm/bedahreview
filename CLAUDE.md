# BedahReview: notes for Claude Code

Phone-first PWA that sorts Indonesian marketplace reviews into Fix / Fight / Ignore (plus Keep) with exact-quote proof and Bahasa drafts, and compares a product with competitors. A PM portfolio piece for Shopee / TikTok: the goal is proof of real, unique users. Standard-library Python server (`src/bedahreview/web.py`), one plain-JavaScript page (`static/index.html`), no build step. Gemini is the model; Supabase holds accounts; Google Cloud Run is the host (live at https://bedahreview-156186000276.asia-southeast2.run.app, deployed by Cloud Build from GitHub `main`; see "Deploy").

## Working rules
- Never put API keys, tokens or the Supabase secret key in code, chat or git. `.env`, `eval/data/`, `eval/results/` and `fetch_cache/` stay untracked. Do not read or print `.env` values; to check it, print key names and set/empty only.
- Do not run a paid fetch (Apify) without asking the owner first; the per-run cost cap is `APIFY_MAX_COST_USD`. Ask before creating or changing anything in the owner's Supabase, Google Cloud or email-sender accounts, and before any deploy; give click-by-click steps, the owner does the clicking. A one-off tiny Gemini request to diagnose an error is fine.
- Run from the venv: `source .venv/bin/activate`. Tests: `python -W ignore -m unittest discover -s tests` (about 90 s, ~340 tests, 4 skipped; the browser tests need Google Chrome). No Node, `gh`, `timeout` or Docker on this Mac.
- After each build step: run the tests, stage the files, scan the staged diff for secrets, draft a commit message. The owner commits and pushes. Commit messages end with the Co-Authored-By line from the session's attribution reminder.
- The owner is a PM, not a developer: plain short answers, one recommendation with reasons, no jargon. When asked to "discuss first" or "do not code", answer without touching files. Report what could not be checked.
- Python changes and `.env` changes need an app restart (Ctrl+C, `python -m bedahreview.web`); the page file is read per request, so a refresh is enough for page-only changes.

## Product rules
- The model returns five buckets (fix, fight, check, ignore, keep); the page shows a 2x2 board: Perbaiki, Tanggapi (check goes under it), Abaikan, Pertahankan. English labels: Fix, Respond, Ignore, Keep ("Fight it" is only the internal bucket name; no "FEATURE 1/2" eyebrows, and "Review checker" instead of "Review triage"). One line "written by AI, read before sending" sits above the drafts of the Fix and Respond tabs; the results footer holds only the link note and the privacy link. Star-only reviews are answered in code (Ignore) and never sent to the model. Likely-fake reviews are left out of every count. Fight it never promises review removal.
- Never log or store review text or reviewer names. The Share menu puts review text in the URL query, so the request log prints the path only. The model env var stays `BEDAHREVIEW_MODEL`.
- The service worker caches the app shell only, never `/api/`.
- UI source of truth: page 6 of the Claude Design canvas (https://claude.ai/artifact/Cm1mSh9f8v8gwPJi8FgRb3, built 2026-11-01). Desktop layout from 900px: a fixed 60/40 split (review triage left, competitors right); below 900px one column (600px max on a tablet held upright, with "Analisis saya / Pesaing" pill tabs) and a bottom bar Bedah ulasan · Tugas · Pesaing. Fonts Plus Jakarta Sans and JetBrains Mono (quotes only) are self-hosted in `static/fonts/` (OFL).
- Results: meta line, one headline built in code (no model change), four equal tiles; a tile opens the group's quotes and drafts in a bottom sheet (side panel from 900px; Back/Escape/scrim close it). Below them "Mulai dari sini · Rencana hari ini": up to 3 steps (Catat a fix: the AI's step is preselected or the seller writes their own, the check date is always 7 days out and shown as one line, no reminder choice; Balas each bad review, counted only when the seller says "Sudah"; Deskripsi, one line from the best praise quote, editable), then a summary. Step 1 offers the model's fix suggestion or the seller's own words (owner decision: no prompt change). Plans live in the browser only (`bedahreview-plans-v1`, ids and counts, no review text, 7 days, cleared on sign-out); the check date goes with the fix (`check_on`; the `remind` column is no longer set, old WhatsApp/calendar values load as "no reminder"). Tugas (owner decision 2026-11-02): an open step is finished on the Tugas screen itself, never by going back into the analysis: a tap opens it in place (log the fix with the AI's step prefilled when that analysis is still on the page; reply drafts with Salin + "Sudah dibalas"; the praise line with Salin + "Sudah ditambahkan"), or, when the analysis is gone, a plain "Sudah kubalas semua" / "Sudah ditambahkan". "Hapus dari Tugas" sets the plan's `skipped` list. Long marketplace titles are cut with `shortLabel()` (full name in the tooltip). "Bedah produk lain" at the end of a plan calls `startFresh()` (clears link, reviews, last result and the competitor panel); "Ulasan baru" only clears the old reviews so the same product still matches its fix. A check-up that has come moves a week on once new reviews of that product are analysed. Each tracked fix is one card (the seller's step as one sentence, one big button "Sudah dikerjakan" or, when the check date has come, "Bedah ulasan terbaru", one small "Cek lagi 8 Nov" line; Ubah and Hapus sit behind "Lainnya"). "Done" is a tick kept in the browser only, like step ticks. "Kirim ke WhatsApp" (Tugas and the summary) opens `wa.me` with a plain-text list of open fixes (product name + the seller's step + check date, newest first, at most 5, never a review quote); we send nothing. "Simpan ke file / Buka dari file" (the old backup) sits under "Lainnya" at the bottom of Tugas and is hidden for signed-in accounts. No WhatsApp reminder, no calendar file. Locked free results show the old "Mulai dari sini" line, not the plan.
- Errors sit under the button that was tapped (link errors on the field itself, Shopee links get an amber "not yet" notice with "Tempel ulasan"); shared text puts the title in Nama produk. Motion: views rise in, steps slide sideways, sheet slides, expanders grow; all off under reduced motion.
- Server errors carry a `code`; the page says known ones in Bahasa/English (`e_<code>` texts), so add a code and both texts when adding an error.

## Accounts, limits and data (Supabase)
- Sign-in: Google first, email 6-digit code as backup, optional skippable intro (platform, shop link, category; no "ok to contact" question). The browser talks to Supabase directly; the server only checks the token itself (`auth.py`: ES256 against the project's cached public keys, needs `PyJWT` + `cryptography`, pinned). Only the user id is kept from a token, never the email. `supabase-js` 2.117.3 is vendored at `static/vendor/supabase.js` (hash checked by a test); the CSP allows connecting to the project's Supabase address only.
- Without `SUPABASE_URL` the app behaves as before (local run open, or shared/per-tester access codes at `/code`). With it, the page is public, a visitor lands in the app (not on the sign-in screen), and every `/api/` call needs a token or an access-code cookie, except the one free analysis below. Open the app at **http://localhost:8000**, not 127.0.0.1 (Google redirects to the address listed in Supabase).
- "Tetap masuk di HP ini" (default on, tucked under "Pengaturan masuk" on the sign-in screen) keeps the session on the device; off keeps it in the tab. iPhone browsers are told to install first and sign in from the icon.
- Free first analysis (owner decision 2026-10-30, the proof-of-users funnel): a visitor without an account gets one analysis, **from a product link or pasted reviews** (owner's call: the link is the main way in, and the link tab comes first on every screen). The reply carries `free: true`; the page shows the counts and the "Mulai dari sini" line, and hides quotes, suggestions and drafts behind a sign-in box (Google or email). The page allows one per browser (`bedahreview-free-used`); the server allows 3 per visitor address and `BEDAHREVIEW_FREE_DAILY` for everyone together (default 30, 0 = off), in memory (`FreeTrial`), address never written. An expired token is asked to sign in again, not treated as a visitor. For Google sign-in the locked result waits in that tab's `sessionStorage` and is removed once shown. After sign-in the page sends `free_unlocked` + `analysed`; `/admin` shows free runs since restart and accounts that unlocked one. Hiding is in the page only (a nudge, not security: the data is the visitor's own reviews).
- Account menu: the header shows "Masuk" to a visitor and a round initial button to someone signed in; it opens Keluar, theme (phone only), Kebijakan privasi, and apart in red "Hapus akun dan data saya" with its confirm step. The email is shown in that browser only. The header's "Tugas" button (open steps + tracked fixes, with a count of open steps and due check-ups) shows from 900px; on a phone Tugas is the middle bottom tab. Language is a small outlined "ID / EN" in the header (under 360px only the current one). A visitor's Tugas asks to sign in (a dialog from 900px).
- Limits: `BEDAHREVIEW_USER_DAILY` analyses per account per day (default 10, 0 = off, day ends midnight Jakarta, in memory, failed analyses are refunded). Every account and the free visitor may read a product link (owner decision 2026-10-30; it costs Apify money, so the daily limit and the free allowance are checked **before** the fetch and given back if it fails). Every signed-in account may also find and compare competitors (owner decision 2026-10-30): a comparison is one of the day's analyses, taken before the paid work and given back on failure; the search step is not counted. A visitor sees "Masuk untuk mencari pesaing" and gets the sign-in screen (the server answers 401). Ids in `BEDAHREVIEW_PAID_USER_IDS` are not daily-limited. The `paid_off` refusal is gone. Global caps stay: 6 analyses at once, hourly caps, `--max-instances 1` on Cloud Run, because limits live in memory.
- Tables (`db/schema.sql`, run by the owner in the Supabase SQL editor, safe to repeat): `profiles`, `events`, `fixes`, `history`, all with row level security and explicit grants ("automatically expose new tables" is off). Never store review text, quotes, drafts, AI suggestions, reviewer names or IP addresses (`history` included). Product name/link and the seller's note are stored only in `fixes`, and the product name alone also in `history` (14 days), by explicit owner decisions; the privacy and terms pages say so. Events are a fixed list in `events.py` (a test compares it with the SQL); `analysis_failed` and `limit_hit` (`SERVER_EVENTS`) are written by the server only, for 5xx failures and 429/503 limits on the three analysis paths, never for DNT/GPC requests, and hold just the step and the error code.
- A policy must never read its own table: Postgres then refuses every insert ("infinite recursion detected in policy", 42P17). This broke every fixes sync and Riwayat save live until 2026-11-02; the per-account ceilings now count through `private.my_fix_count()` / `private.my_history_count()` (security definer, own rows only, a schema the API does not expose). The fake Supabase in the tests does not run policies, so only a live check proves a policy change.
- Owner dashboard `/admin` (`admin_stats.py`, `static/admin.html`, English only): on only with `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` and `BEDAHREVIEW_ADMIN_USER_IDS`; the page holds no data, `/api/admin/stats` needs a Supabase token of a listed id, everyone else gets the same 404. Reads accounts (email dropped at once), events, profiles (not the shop link) and fixes (dates only) with the secret key; returns totals, 8-character ids and feedback comments; admin ids are left out of every number; cached 60 s. Access-code testers are not on it.
- Events: the page queues them and sends batches (`/api/events`, every 10 s and when hidden); the server prints a log line for each and saves rows for signed-in accounts from a background thread (`event_store.py`, needs `SUPABASE_SERVICE_KEY`; failures are dropped with one warning). Supabase being down or paused must never break analysing.
- Fixes live in the browser first and sync to the account (merge on sign-in, newer copy wins; a browser that held another account's list is never mixed in). Notes cannot repeat review text. `check_on` needs `db/schema.sql` re-run; until then the page saves without them (falls back on a missing-column error) and keeps the check date in the browser.
- Riwayat (`history`, added 2026-11-02): after each analysis a signed-in seller's page saves one row with their own token (date, product name, reviews, fix_n/fight_n/ignore_n/keep_n, top_theme = a fixed theme name or null; `HISTORY_COLS` in the page, a test compares it with the SQL). A failed save is silent. 14 days: the page deletes older rows when Riwayat opens or a row is saved and never shows them; an optional `pg_cron` line in the schema (commented out, not verified) cleans up sellers who never return. Opened from the account menu (top item) and a link at the top of Tugas; hidden without an account. "Bedah lagi" opens the paste screen with the product name; old results cannot be reopened. Event `history_opened` (no fields).
- "Hapus akun dan data saya" (`account.py`): deletes the rows, then the account, revokes the token at once, clears the browser copy. `/privacy` is a public bilingual page; `BEDAHREVIEW_CONTACT_EMAIL` publishes a contact address (leave empty to publish none).
- The secret key (`SUPABASE_SERVICE_KEY`) is server-only: never in a page or a reply (a test checks this).

## Background analysis and batching (added 2026-10-30)
- `POST /api/classify` with `"async": true` (what the page sends) answers 202 `{job}` at once; `GET /api/job/<id>` returns `running` (step, done, total), `done` or `failed` (the exact status and body the plain request would have sent). Without the flag the request is synchronous as before. Jobs are in memory only (`Jobs`, 10 minutes, 200 at most), the id is a 32-hex capability token (open to a visitor without an account, kept out of the request log), and a job holds one analysis slot until it ends. The page keeps the id in localStorage (`bedahreview-job`) and resumes polling after a reload. The privacy page says results sit in server memory up to 10 minutes.
- Batches are up to 20 reviews (`BATCH_SIZE`); `make_batches` keeps reviews that share a template together so the fake check sees them. Changing batching or the prompt means re-running the eval (spends Gemini credit: ask first). The eval has NOT been re-run since the batch change (15 -> 20 grouped).
- User-facing text says "AI service", not the provider's name; the privacy page says a paid third-party AI service, not used for training under the provider's paid terms, kept briefly for abuse and legal checks (checked against Google's Gemini API terms on 2026-10-30; the key's Cloud project must keep active billing for that to hold).
- The paste screen shows "N reviews found" (same split as the server); fix tracking says "indicative, not proof".
